## 扫码模式实现说明

### Problem

原程序以抓包 cURL 提供身份和阅读参数，Docker 环境更新不便；续期仅更新会话内存，下一会话仍从原始 cURL 加载。

### Decision

扫码模式在 `weread-bot.py` 中直接调用官网登录接口，通过阅读页 JSON 状态和书架/目录/进度接口准备阅读请求。网页使用 aiohttp 与现有 asyncio 循环共享进程，二维码由本地 qrcode 生成；运行时代码仍为单文件。原 cURL 路径继续独立运行。

登录和选书改变凭据代际，续期只能更新同一代际的 Cookie。持久化先写同目录临时文件，flush/fsync 后原子替换；写入失败不更新内存。旧会话先停止再安装新登录，防止旧 Cookie 回写。二维码流程独立持有会话和标识，取消后的响应不能生效。

扫码 UID 获取和确认长轮询独立于阅读限速。将两者套用默认每分钟 10 次的限速，会在二维码显示与确认监听之间插入约 6 秒空档，实测出现快速扫码失败、等待 10 秒后成功的差异。实现仅豁免这两个固定的登录 GET 接口，其他请求继续限速；回归测试阻塞阅读限速器，验证登录握手仍能立即发出，而阅读请求必须等待。阶段日志记录准备、等待确认、验证凭据和结果，不记录 UID、验证码或 Token。

网络与协议失败不等同认证失效。只有明确认证错误才暂停并发一次重新扫码提醒；页面与调度触发共用一条阅读通道，守护模式每日次数保存在状态文件中。

每日首场时间通过 `daemon.daily_start_time` 表达，复用原有会话间隔和每日上限。空值保留全天运行语义；设置时间后以 `schedule.timezone` 为准，错过首场可补跑，满额或跨日后等待下一天的起始时间。扫码模式将下一场时间及调度参数摘要与凭据状态一起原子保存：重启恢复已经抽取的间隔，配置变化才重新计算；会话开始时先计次并清空旧计划，若进程中断则保守等待完整间隔，避免重复执行。它采用应用内调度，避免宿主机 cron 停启整个容器造成管理页面离线。

### Alternatives considered

- 后台浏览器可以自动抓取参数，但增加镜像与内存开销，且用户明确选择直接接口。
- 重写 cURL 文件虽改动少，但首次仍需抓包，也无法可靠管理动态阅读参数。
- 新增独立服务或拆分 Python 包会违背本仓库单运行文件约定，并增加部署步骤。
- 将三个时段写死为 cron 不能满足“读完后再随机休息”的语义；每日首场和后续间隔应在同一调度流程中计算。

### Consequences

使用者首次和续期都可扫码，凭据能随 Docker 数据目录持久化；代价是维护官网非公开接口和阅读页结构的兼容性。管理页面依赖 HTTPS 反向代理，程序不内置证书管理。实现将异常响应作为显式失败，不执行网页脚本、不回退到硬编码阅读参数。

测试在 `tests/` 中覆盖登录、验证码、过期与取消、原子存储、代际保护、动态签名、管理入口认证和调度合并。真实账号验收需另行扫码，不能用模拟接口通过替代真实验证。
